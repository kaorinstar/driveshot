# 設計方針

[English version](architecture.md)

## リポジトリの構成

3つの層に分かれます。上の2つの境界が、他のすべての判断の基準になります。

```
src/                      設定ウィンドウ。HTML・CSS・TypeScript。受け取った答えを表示する。
  ↓  invoke()
src-tauri/                アプリ本体。常駐、ホットキー、画面取り込み、クラウド通信、ファイル操作。
  ↓  通常の関数呼び出し
crates/driveshot-core/    判断を行う層。ウィンドウ・ネットワーク・OSのAPIに依存しない。
```

呼び出しは必ず下向きです。core側はTauriを知らず、ウィンドウ側はアップロードの仕組みを知りません。

### なぜcoreを分けるか

`crates/driveshot-core` の内容は、どのOSでもビルドでき、テストも実行できます。このプロジェクトの
作業で多く使うLinuxでも同じです。これは手間を減らすためではなく、Driveshotの中で最も危険な処理を
検証可能にするためです。「保存期間を過ぎた」という判断は、誤れば利用者の画像を消します。そして
この判断は、時刻を受け取って結果を返すだけの関数として書けます。実際にそう書き、境界値ごとに
テストを用意しています。

追加時の判断基準は次のとおりです。画面・ファイル・ネットワークなしで書けるなら、core側に置きます。
`src-tauri` に残すのは、それらがどうしても必要な部分だけです。

### 現在coreにあるもの

| 型 | 何を判断するか |
|---|---|
| `Provider` | どのクラウドドライブへ保存したか。記録用の識別子も持つ |
| `Retention` | 保存期間と、削除の対象になる時刻 |
| `ShotRecord` | 1件のアップロード記録。ファイル、保存先、時刻、共有URL、保存期間 |
| `ShotIndex` | 未削除のアップロード全件と、そのうち削除対象となるもの |

次の2点は意図的な設計です。理由なく変更しないでください。

- **保存期間0日は表現できません。** `Retention::Days` は `NonZeroU32` を持つため、入力欄が空の場合
  や設定ファイルに `0` が入っていた場合でも、「いまアップロードしたものを即削除する」という意味に
  はなりません。呼び出し側それぞれで確認するのではなく、型が受け付けません。
- **日付として表現できない期限は、削除しない扱いにします。** 非常に大きな日数を加算すると、
  暦の表現範囲を超えます。この場合は「期限なし」として扱い、「期限切れ」とは扱いません。後者では、
  利用者が保持を指定したファイルを削除してしまうためです。

### バージョン番号の置き場所

`src-tauri/Cargo.toml` の `[package]` セクションだけです。`src-tauri/tauri.conf.json` には意図的に
バージョンを書いていないため、Tauriのバンドラーはここを読みます。`.github/workflows/release.yml`
が、タグの値でこの1行を書き換えます。2か所に書けば、2か所で書き忘れが起きます。

## まだ実装していない機能

Driveshotの目的である4つの機能は、いずれも未実装です。

1. 画面の一部を**取り込む**。
2. OAuth認証を通じてクラウドドライブへ**アップロードする**。
3. ファイルを「リンクを知っている人は閲覧可」に設定し、URLを取得して**共有する**。
4. 保存期間を過ぎたら**削除する**。

現在のウィンドウは、3つの保存先を一覧表示し、いま撮った画像がいつ削除されるかを表示します。
どちらの答えもcoreが計算し、`src-tauri/src/main.rs` の2つのTauriコマンド経由で渡しています。
これは意図した骨組みです。難しい処理を書く前に、ウィンドウからcore、テスト、CI、インストーラー
までの経路を実際に動く形で確認できます。

## 未決定の2点

どちらも、決めなくても開発は進められます。ただし決め方によって作るものが変わるため、記録して
おきます。

### 最初に対応する保存先の数

Googleドライブ、OneDrive、Dropboxは、認証方法・アップロード方法・共有URLの発行方法がそれぞれ
異なります。`Provider` には最初から3つすべてを定義しています。保存先の識別子はすべての記録に
書き込まれるため、いま書いた記録が後から読めなくなることを避けるためです。どれを先に実装するか、
残り2つをすぐ続けるかは未決定です。

1つずつ進める方が負担は小さく、動くアプリを早く用意できます。3つ同時に進めると、最初の1つに
引きずられない抽象化を作らざるを得ません。

### 削除処理をどこで実行するか

保存期間の仕組みがあるからこそ、公開状態の共有URLを許容できます。つまり、どれだけ確実に実行
できるかが論点です。

- **アプリ内で完結する方式。** Driveshotが動いているときに、期限切れのファイルを削除します。
  追加で用意するものはなく、サーバーの費用も運用も不要です。ただし、期限を過ぎてもパソコンの
  電源が入っていなければ、次回起動時まで削除されません。
- **サーバーを併用する方式。** 小規模なサービスが期限を管理し、利用者のパソコンの状態に関係なく
  削除します。保存期間が文字どおりの意味になります。その代わり、運用するサービスが1つ増え、
  そのサービスが利用者のクラウドドライブへのトークンを保持することになります。これは、自分の
  トークンだけを持つデスクトップアプリとは、責任の重さが大きく異なります。

後者は前者の小さな拡張ではありません。Driveshotの性質が変わります。利用者のパソコンと利用者の
ドライブだけに触れるアプリから、他者のストレージへの認証情報を預かるサービスになります。採用する
場合は、その機能を含むリリースの前に `SECURITY.ja.md` へ明記する必要があります。

決定するまでの間、coreはどちらでも構築できるように書いてあります。`ShotIndex` は「この時刻の
時点で削除対象となるものはどれか」に答えるだけで、削除自体は行いません。呼び出す側が、定期実行
するアプリなのか別の仕組みなのかは、未定のままにしてあります。
